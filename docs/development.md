# Development

## Prerequisites

| Tool | Used for | Tested with |
| --- | --- | --- |
| Go | building and testing | see `go.mod` |
| Docker | runs the kind nodes | any recent Docker Engine or Docker Desktop |
| [kind](https://kind.sigs.k8s.io/) | local Kubernetes cluster | v0.33.0 |
| kubectl | talking to the cluster | a version within one minor of the cluster |

## Local cluster

```sh
make kind-up      # create the cluster "vesper-dev" (does nothing if it exists)
kubectl --context kind-vesper-dev get nodes
make kind-down    # delete it (does nothing if it does not exist)
```

Use another name with `make kind-up KIND_CLUSTER=other`. The kubectl context is
always `kind-<name>`.

### Kubernetes version

The Kubernetes version is set by the node image in `hack/kind-config.yaml`. It
is pinned by tag and by digest so that every contributor and CI test the same
version. To upgrade, take the image listed in the release notes of the new kind
version and update the file and the table above.

## Operator layout

The operator (the "manager") was scaffolded with Kubebuilder v4 (see
[ADR-0001](adr/0001-use-kubebuilder.md)). The scaffold that Kubebuilder writes
by itself is kept as generated; files that duplicate the repository's own
conventions (README, Makefile, CI workflows, lint config) were not taken.

| Path | What it is |
| --- | --- |
| `cmd/main.go` | Entry point of the manager: builds the controller-runtime manager (API client, cache, health probes on `:8081`, metrics, optional leader election) and runs the controllers. Kubebuilder edits it when an API is added, at the `+kubebuilder:scaffold:` markers, so it stays at this path. |
| `api/v1alpha1/` | The `PreviewEnvironment` API as Go types. The CRD is generated from them. `zz_generated.deepcopy.go` is generated: do not edit it. |
| `cmd/vesperctl/` | The CLI. |
| `PROJECT` | Kubebuilder's record of what was scaffolded (domain, module, APIs). Its commands read it; do not edit it by hand. |
| `config/` | Kustomize manifests to deploy the operator: `manager/` (its Deployment), `rbac/` (ServiceAccount and roles), `default/` (the overlay `make deploy` applies, with the metrics Service), `network-policy/` and `prometheus/` (optional, off by default), `crd/` (the generated CRD) and `samples/` (an example `PreviewEnvironment`). |
| `config/rbac/role.yaml` | Generated by `make manifests` from the `+kubebuilder:rbac` markers. Do not edit it by hand. |
| `hack/boilerplate.go.txt` | License header that `make generate` puts on generated Go files. |
| `Dockerfile` | Builds the manager into a distroless image that runs as a non-root user. |

Generated files are rebuilt from the Go code:

```sh
make manifests   # CRD and RBAC YAML from the Go types and +kubebuilder markers
make generate    # DeepCopy methods of the API types
```

`make build` runs both before compiling, and installs `controller-gen` (and
`kustomize` for the deploy targets) into `bin/` at a pinned version the first
time.

### Run the operator

```sh
make build                  # bin/vesperctl and bin/manager
make run                    # run the manager on your machine, against the current kubectl context
make docker-build IMG=vesper-manager:dev
```

`make run` uses whatever cluster your current kubectl context points to: check
it with `kubectl config current-context` first. It reconciles every
`PreviewEnvironment` of that cluster, and writes their status. Stop the manager
with Ctrl-C. Its health probes answer on `curl localhost:8081/healthz`.

### What the operator does

The controller is in `internal/controller`. For each `PreviewEnvironment` it:

1. creates a dedicated namespace named `vesper-<namespace>-<name>-<hash>`
   (`NamespaceName` in `naming.go`): truncated to 63 characters, with an
   8-character hash of `<namespace>/<name>` so that two previews never share a
   namespace. The same preview always gets the same name;
2. labels it with the preview labels (see
   [How Vesper tracks preview objects](#how-vesper-tracks-preview-objects))
   and with `pod-security.kubernetes.io/enforce=restricted`;
3. creates or updates a Deployment named `app` in it (`deployment.go`): the
   image, the port (named `http`), the environment variables and the replicas
   of the spec. Its pods run with the restricted Pod Security settings:
   `runAsNonRoot`, no privilege escalation, all capabilities dropped, the
   `RuntimeDefault` seccomp profile and no ServiceAccount token. **The image
   must run as a non-root user**: an image that runs as root, such as the
   official `nginx`, stays in `CreateContainerConfigError`
   (`nginxinc/nginx-unprivileged` works);
4. creates or updates a ClusterIP Service named `app` in front of the pods
   (`service.go`): port 80, which targets the container port by its name
   (`http`), so the Service stays the same when `spec.port` changes. Its
   address, `http://app.<preview namespace>.svc.cluster.local`, is written to
   `status.internalURL` (`kubectl get pe -o wide`). It is reachable from inside
   the cluster only; the public address (`status.url`) comes with an Ingress
   in P3;
5. sets the phase to `Ready`, with the `Ready` condition `True`
   (`DeploymentAvailable`), when every replica runs the requested image, and
   to `Pending` (`Provisioning`, for example "0/2 replicas available") until
   then.

The Deployment is written with `controllerutil.CreateOrUpdate`, which sets only
the fields Vesper owns and keeps the defaults the API server adds, so a
reconciliation that changes nothing writes nothing.

If a namespace of that name exists without the labels of that preview, the
operator does not touch it: the phase becomes `Failed` with the reason
`NamespaceConflict`. A namespace, a Deployment or a Service deleted or changed
by hand is restored. To reach a preview from your machine before it has a
public address:

```sh
kubectl port-forward -n <preview namespace> svc/app 8080:80
```

Not yet: a public address (P3), and deleting a preview leaves its
namespace. Cleanup on deletion comes with a finalizer in P3; until
then, delete it with
`kubectl delete namespace -l vesper.eventide.dev/preview-namespace=<namespace>,vesper.eventide.dev/preview-name=<name>`.

### How Vesper tracks preview objects

Every object Vesper creates for a preview (the namespace, the Deployment, its
pods and the Service) carries the same three labels, set by
`setPreviewLabels` in `labels.go`:

| Label | Value |
| --- | --- |
| `app.kubernetes.io/managed-by` | `vesper` |
| `vesper.eventide.dev/preview-namespace` | namespace of the `PreviewEnvironment` |
| `vesper.eventide.dev/preview-name` | name of the `PreviewEnvironment` |

Kubernetes usually ties an object to its owner with an owner reference, and
its garbage collector deletes the object when the owner is deleted. Vesper
cannot use one:

- a namespaced object can only be owned by an object in the same namespace.
  The preview lives in your namespace (`team-a`), its Deployment and Service
  in the preview namespace (`vesper-team-a-pr-42-<hash>`). Kubernetes treats
  such a reference as invalid, and the garbage collector may delete the
  object, thinking its owner is gone;
- the preview namespace is cluster-scoped, and a cluster-scoped object cannot
  have a namespaced owner.

The labels replace the owner reference:

- **Ownership.** Before it modifies an object, the operator checks that it
  carries the labels of this preview (`ownedBy`). It never takes over an
  object someone else created: it reports an error, or `NamespaceConflict` for
  a namespace.
- **Watches.** A change to a labeled object reconciles its preview, found from
  the labels (`previewOfObject`).
- **Selection.** `kubectl get ns,deploy,svc -A -l app.kubernetes.io/managed-by=vesper`
  lists everything Vesper created.
- **Cleanup.** The preview namespace is the cleanup boundary: deleting it
  deletes everything in it. Deleting the namespace when its preview is deleted
  is the job of a finalizer
  ([#39](https://github.com/eventide-oss/vesper/issues/39)).

### Change the API

The Go types in `api/v1alpha1/previewenvironment_types.go` are the source of
truth for the `PreviewEnvironment` API:

- the JSON tag of a field is its name in YAML;
- its comment becomes the documentation shown by
  `kubectl explain previewenvironment.spec`;
- `+kubebuilder:validation:` markers, including CEL rules
  (`XValidation`), and `+kubebuilder:default` markers become the validation
  and defaults that the API server applies.

After a change, regenerate and commit the generated files:

```sh
make manifests generate   # CRD, RBAC role (from the +kubebuilder:rbac markers) and DeepCopy methods
make verify-generated     # what CI runs: fails if a generated file is not committed
```

CI runs `make verify-generated` on every pull request: it regenerates the
files with the controller-gen version pinned in the Makefile and fails if
they differ from the committed ones, so a forgotten `make manifests generate`
cannot reach `main`. The year in the license header of generated files is
fixed (`YEAR` in the Makefile) so that the files do not change every January.

To try the validation by hand on the kind cluster:

```sh
make install                                  # install or update the CRD
kubectl --context kind-vesper-dev create --dry-run=server -f config/samples/vesper_v1alpha1_previewenvironment.yaml
```

`--dry-run=server` runs the API server's validation and defaulting without
storing the object. `make uninstall` removes the CRD and every
`PreviewEnvironment` with it.

## Tests

```sh
make test               # unit and controller (envtest) tests, no cluster needed
make test-integration   # vesperctl against the kind cluster (created if missing)
```

### Controller tests (envtest)

The controller has two kinds of tests in `internal/controller`:

- **Unit tests** call `Reconcile` directly against the fake client of
  controller-runtime, an in-memory store. They are fast and cover the edge
  cases, but the fake client does not validate the CRD schema, add server
  defaults or run the watches.
- **envtest tests** (`envtest_test.go`) start a real `kube-apiserver` and
  `etcd` with the generated CRD, and run the controller in a real manager, as
  in production. A test creates a preview and waits for the result with
  `eventually` (retries every 100 ms, fails after 10 s), never with a fixed
  sleep. `TestMain` in `suite_test.go` starts envtest once for the package.

envtest runs no other controller. There is no Deployment controller, so no
pod ever runs: a test writes the Deployment status itself to make a preview
`Ready`. There is no namespace controller, so a deleted namespace stays
`Terminating`: each test creates its own namespace (`team-<random>`) and
never deletes it.

`make test` downloads `setup-envtest` and the `kube-apiserver` and `etcd`
binaries of Kubernetes `ENVTEST_K8S_VERSION` into `bin/`, and points the tests
to them with `KUBEBUILDER_ASSETS`. A plain `go test ./...` skips the envtest
tests; in CI (`CI` set), they fail instead of being skipped. To run them
from your editor or with other flags:

```sh
make setup-envtest
export KUBEBUILDER_ASSETS="$(bin/setup-envtest use 1.37.0 --bin-dir bin -p path)"
go test -race -run Envtest -v ./internal/controller/
```

### Integration tests

The integration tests in `test/integration` sit behind the `integration` build
tag, so `go test ./...` skips them. They build the `vesperctl` binary and run
`list` and `get` against a real API server, with the generated CRD of
`config/crd/bases`. They create previews, then write their status through the
status subresource, as the operator would.

Each run creates a namespace named `vesper-it-<random>` and a few previews,
and deletes them at the end, even when a test fails. Everything it creates
carries the label `app.kubernetes.io/managed-by=vesper-integration-tests`.

- If no `PreviewEnvironment` CRD is installed, the tests install it, with that
  label, and delete it at the end. Deleting a CRD deletes every
  `PreviewEnvironment`, so the tests only delete a CRD that carries their
  label.
- If a CRD without the label is installed (for example with `make install`),
  it is left in place, with its previews, and the "not installed" cases are
  skipped.
- A labeled CRD left by an interrupted run is removed before the tests start.
  Never add that label to a CRD yourself.
- Stop the operator (`make run`) before you run them on the same cluster: it
  would reconcile the test previews, overwrite the status the tests set, and
  create namespaces for them that stay after the run (until #39).
- The tests only run against a context named `kind-...`; they refuse any
  other cluster. `VESPER_IT_CONTEXT` selects the context, and
  `make test-integration KIND_CLUSTER=other` sets it for you.

CI runs them on every pull request, in the `integration` job.
